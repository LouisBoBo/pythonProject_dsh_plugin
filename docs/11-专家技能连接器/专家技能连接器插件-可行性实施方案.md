# 专家 · 技能 · 连接器插件：可行性实施方案

> **状态**：方案已确认，P0 开工（2026-09-18）  
> **已拍板**：① P0 售后工单分析 + 测试用例生成都做；② MES 按公司现有只读接口对接（可 mock 兜底）；③ Dify 暂无 datasetId，配置页 + 未配置降级、禁止编造检索结果；④ 与 `mes_pcb` 并存，不替换。  
> **落点**：本仓库独立 DSH Bundle `@zhongruan/dsh-esc`（目录 `dsh-esc/`）  
> **对照源**：腾讯 WorkBuddy「专家-技能-连接器」；本文附图口径（专家=脑子、技能=手册、连接器=手脚）  
> **交付形态**：公司插件市场安装；**零改** `DSH-ZR-WorkBuddy`；**不改** 现有公司插件源码  
> **产品一句话**：给大模型按需注入「岗位角色、SOP 手册、外部手脚」，围绕 PCB 制造与办公，先打通 Dify/MES 取数 + 售后工单分析 / 测试用例生成。

---

## 0. 这是什么、不是什么

| 是 | 不是 |
|----|------|
| 一套**可安装的 DSH 插件**：侧栏入口 + 预制专家/技能/连接器 + 对话时注入上下文与工具 | 改 WorkBuddy 引擎、`features/`、`.dsh/skills/`、`mes-bridge` |
| 对标腾讯 WorkBuddy 的**三层解耦**（专家 / 技能 / 连接器） | 把腾讯客户端、MCP 市场、专家团社区整包搬过来 |
| PCB 行业 + 办公场景的**预制资产**（可后续自建） | 替代已有 `mes_ask` / `mes_pcb` / `pcb_8d_*` / 知识库 / 写码 / 自动化 |
| 连接器 = 标准 HTTP 适配 + DSH `tools.register`（MCP 语义） | P0 就自建完整 MCP 进程与第三方连接器商店 |

一句话原理（与附图一致）：

> 三者本质都是「注入给模型的上下文」：专家 = 人设与方法论，技能 = 按需加载的操作手册，连接器 = 可调用的外部工具。

## 1. 硬约束（不可协商）

| # | 约束 | 本方案如何满足 |
| --- | --- | --- |
| 1 | **不动 WorkBuddy 任何功能** | 不改 `DSH-ZR-WorkBuddy`；不调 `mesEngine`；不往 `.dsh/skills/` 写文件；不替代 `mes_pcb` / `mes_ask` |
| 2 | **不影响其它公司插件** | 新目录 `dsh-esc/`；工具名前缀 `zr_esc_`；侧栏 slot id `esc`；端口 **18786**；独立数据目录；打包只加本包，不 FORCE 上传 |
| 3 | **界面交给 DSH 原生壳** | 不写 Electron、不新开桌面窗。管理面 = `sidebar.footer.action`「专家·技能·连接器」；对话面 = 系统提示注入 + 工具卡 |
| 4 | **独立插件、市场可装** | `dsh.bundle` + `dshMarket`；`pack.sh dsh-esc` → `upload.sh`；本机可 mock 跑通 |
| 5 | **聊天认 DSH，资产认本机库** | 会话树仍是 DSH；专家/技能/连接器定义与启用状态在本机 JSON。禁止另造聊天会话 |
| 6 | **契约字段权威** | 启用/选中只认 `expertId` / `skillId` / `connectorId` / `enabled` / `status`；禁止用用户原话正则猜「取消专家」「换成售后」 |
| 7 | **终态与隔离** | 连接器写操作（若有）未确认不得落库；失败只记 `error.code`。禁止改写其它插件 Job / 知识库文档 / 8D 草稿 |
| 8 | **计量口径冻结** | 不改 `dsh-llm-meter` 公式；本插件不绕过 `llm/stream` |

## 2. 对照：腾讯 WorkBuddy × 本公司现状 × 本插件

### 2.1 腾讯 WorkBuddy（必须对齐的产品机制）

| 腾讯能力 | 本插件是否做 | 说明 |
|----------|--------------|------|
| 侧栏统一入口「专家-技能-连接器」 | **P0** | 一个入口、三个页签（精选场景 / 专家 / 技能 / 连接器） |
| 专家 = 岗位人设，会话选定后全程带着 | **P0** | `system-prompt/assemble` 注入；按 DSH `sessionId` 记住当前专家 |
| 技能 = `SKILL.md`，命中才加载全文 | **P0** | 目录只注入摘要；命中后 `agent/pre-step` 注入全文（有界） |
| 连接器 = MCP 工具，模型自主调用 | **P0 语义对齐** | DSH `defineTool` 暴露函数；P2 再接标准 MCP Server |
| 精选场景卡片（专家+技能+连接器组合） | **P0** | 预制 3 张场景卡，一点启用整套组合 |
| 专家团市场 / 社区作者 | **不做（本阶段）** | 只做公司预制 + P1 本机新建 |
| 第三方 MCP 商店（微信支付等） | **不做（本阶段）** | 只做公司系统：Dify / MES /（P1）企微、报价 |

### 2.2 本公司已经有的、禁止抢戏

| 现网能力 | 归属 | 本插件关系 |
|----------|------|------------|
| `mes_ask` 自然语言查 MES | WorkBuddy feature `mes-ask` | **并存**。本插件 MES 连接器默认关闭；用户在 ESC 面板启用后才注册 `zr_esc_mes_*` |
| `mes_pcb` PCB 工艺问答 | feature `mes-pcb` + 引擎 `pcb_expert.py` | **并存**。本插件「PCB 工艺顾问」是提示词人设，不调引擎 |
| `pcb_8d_*` 8D 报告 | `@zhongruan/dsh-pcb-8d` | 技能文案可**引导**用户走 8D 插件，代码不 import、不改其草稿目录 |
| 知识库 RAG | `@zhongruan/dsh-knowledge` | Dify 连接器独立 HTTP；P1 可选探测知识库，未装不影响 |
| 写码 / 审码 / 自动化 / 用量 | 对应独立插件 | 工具白名单禁止调用 `zr_cursor_*` / 审码 / 自动化写接口 |
| 路由 Skill `zr-workbuddy-routing` | WorkBuddy `.dsh/skills/` | **不改**。本插件用自己的摘要 + 专家上下文做分流 |

### 2.3 为什么不把技能写进 WorkBuddy 的 `.dsh/skills/`

1. 那会改宿主仓库，违反硬约束 1。  
2. 技能只在「工作区正好是 WorkBuddy 仓」时出现，装插件的其它工程看不见。  
3. 会污染现网写码/查数路由。  

因此：**技能文件打进本插件包** `dsh-esc/assets/skills/<id>/SKILL.md`，由插件按需注入。

## 3. 目标体验

### 3.1 用户路径（对标附图 + WorkBuddy 精选场景）

```text
设置 → 插件市场 → 安装「专家·技能·连接器」
  → 左侧栏出现入口（与知识库、自动化并列）
  → 打开面板：精选场景 | 专家 | 技能 | 连接器 | 设置

路径 A · 精选场景（主路径）
  点「售后工单分析」→ 一键启用：售后专家 + 工单分析技能 + MES/Dify 连接器
  → 回对话：「帮我分析这张售后单……」→ 模型按 SOP 取数、归纳、出报告

路径 B · 自己拼
  先选「PCB 工艺顾问」→ 再打开「测试用例生成」技能 → 需要时启用 Dify
  → 对话自然进行，无需记工具名

路径 C · 对话切换（P1）
  「换成需求分析专家」→ 模型调 zr_esc_select_expert(expertId=req-analyst)
  → 只认工具参数里的 expertId，不扫用户正文里的「换成」
```

### 3.2 一次任务里三者如何配合（验收剧本）

**剧本 1：售后工单分析（P0 首选）**

```text
售后支持专家（定分析框架：分类 / 根因 / 对策 / 是否升级 8D）
  → 售后工单分析技能（SOP：取工单 → 拉工序/良率 → 查知识库相似单 → 出结构化报告）
  → MES 连接器（工单/工序/不良）+ Dify 连接器（历史对策）
  → 模型综合成 Markdown 报告（可复制；P1 再落知识库）
```

**剧本 2：测试用例生成（P0 并行可做）**

```text
测试专家（用例方法论：等价类 / 边界 / 工序异常 / 回归）
  → 测试用例生成技能（按公司模板出表）
  → Dify 连接器（需求/工艺规范）
  → 输出用例表（编号、前置、步骤、期望、优先级）
```

**剧本 3：报价助手（P1，等报价接口）**

```text
项目经理助手 → 报价单生成技能 → 报价系统连接器 + 历史报价
```

### 3.3 空态文案

- 标题：给 AI 配上岗位、手册和手脚  
- 副文：专家决定谁来做，技能决定怎么做，连接器决定去哪取数。三者解耦，全公司复用。  
- 未配连接器时：场景卡可点，对话能出框架；取数步骤返回 `error.code=connector_unconfigured`，**不编造 MES/Dify 数据**。

## 4. 架构

```text
┌─────────────────────────────────────────────────────────────────┐
│  DSH 原生壳                                                       │
│  · sidebar.footer.action id=esc  「专家·技能·连接器」            │
│  · 主面板：场景 / 专家 / 技能 / 连接器 / 本机设置                 │
│  · 对话：无专用聊天树；只注入 prompt + 注册工具                   │
└──────────────────────────────┬──────────────────────────────────┘
                               │ 127.0.0.1:18786
┌──────────────────────────────▼──────────────────────────────────┐
│  Bundle @zhongruan/dsh-esc                                       │
│  · Catalog：预制专家 / 技能 / 连接器 / 场景（只读资产）          │
│  · Store：启用状态、当前专家(sessionId)、连接器密钥（脱敏）      │
│  · Prompt：system-prompt/assemble + agent/pre-step（有界）       │
│  · Tools：zr_esc_* （仅已启用连接器 + 选择/查询类工具）          │
│  · Adapters：mock | http  （MES / Dify / 企微）                  │
└─────────────┬─────────────────────────────┬─────────────────────┘
              │                             │
     公司 MES / 报价 HTTP              Dify 知识库 HTTP
     （无配置则 mock 演示）             （无配置则跳过检索）
```

### 4.1 运行时注入（已有插件验证过，风险低）

与 `@zhongruan/dsh-knowledge` 同一条官方瀑布，**不得**改知识库插件：

| 时机 | 事件 | 注入什么 | 上限 |
|------|------|----------|------|
| 每轮拼系统提示 | `system-prompt/assemble` | 当前专家人设 + 已启用技能**一行摘要** + 已启用连接器名单 | 专家 ≤ 4KB；技能目录 ≤ 2KB |
| 本轮用户话命中技能触发 | `agent/pre-step`（仅 step=1） | 命中技能的 `SKILL.md` 全文 | 单技能 ≤ 8KB；每轮最多 1 个（P0） |
| 模型决定调工具 | DSH tools | 仅 **enabled=true** 的连接器工具 | 未启用的不 `register` |

命中规则（窄，禁止扫全文启发式）：

1. 用户显式 `/技能名` 或面板「在本会话使用」写入的 `activeSkillId`。  
2. 技能 front-matter 的 `triggers[]` 与用户**本轮原文**做**短语包含**（短词表，不是「取消|分析|工单」这种过宽正则）。  
3. 都未命中 → 不加载全文，只留摘要，让模型决定要不要请用户打开某技能。

**禁止**：用技能正文或模型结论里出现「取消」来卸载专家；卸载只认面板开关或 `zr_esc_select_expert` 的 `expertId`。

### 4.2 为什么连接器先做成 DSH Tool 而不是真 MCP 进程

| | P0 DSH Tool | 真 MCP Server |
|--|-------------|---------------|
| 模型怎么调 | `ctx.tools.register` | MCP 发现后再 register（DSH 官方也是这条） |
| 安装 | 本插件装上即有 | 多一个进程/端口/协议排障 |
| 公司 MES | 一层 HTTP 适配即可 | 还要维护 MCP SDK |
| 以后 | Adapter 接口保持 `listTools/callTool` | P2 把同一 Adapter 挂到 `@modelcontextprotocol/sdk` |

P0 就把每个连接器做成 **「MCP 形态的工具清单」**（name / description / inputSchema / execute），接口预留，避免以后推翻。

### 4.3 本机 HTTP 职责

默认 **`127.0.0.1:18786`**，避开：

| 端口 | 占用方 |
|------|--------|
| 18787 | `dsh-remote-review` |
| 18788 | `dsh-cursor-coding` |
| 18789 | `dsh-automations` |

| 方法 | 路径 | 用途 |
|------|------|------|
| GET | `/health` | 版本、已启用连接器、当前端口 |
| GET | `/api/catalog` | 预制专家/技能/连接器/场景（无密钥） |
| GET/PUT | `/api/session-state` | 按 `sessionId` 读写当前专家、启用的技能/连接器 |
| GET/PUT | `/api/connectors/:id/config` | 连接器地址与密钥（回读脱敏） |
| POST | `/api/connectors/:id/test` | 测连通；失败 `error.code=connect_failed` |
| GET | `/api/settings` | 端口、mock 开关 |

面板只打这个本机口。对话工具走 Cordis，不经过 WorkBuddy `:8000`。

## 5. 数据模型

存储目录：`~/.dsh/esc/`（或 profile 下 `data/esc/`），原子写（`.tmp` + `rename`）。

**禁止**写入：

- `~/.workbuddy/`
- `~/.zhongruan/pcb-8d-drafts/`
- 知识库 sqlite
- 写码 / 审码 / 自动化的 jobs 目录
- WorkBuddy `engine/data/`

### 5.1 `catalog`（随包只读）

```text
dsh-esc/assets/
  experts/<id>/EXPERT.md      # YAML front-matter + 人设正文
  skills/<id>/SKILL.md        # 标准 Skill 格式
  connectors/<id>/manifest.json
  scenes/<id>.json            # 精选场景：绑定 expertIds / skillIds / connectorIds
```

`EXPERT.md` 权威字段：

| 字段 | 含义 |
|------|------|
| `id` | 稳定主键，如 `pcb-process-advisor` |
| `title` | 展示名 |
| `role` | 岗位 |
| `tags` | 场景标签 |
| `preferredSkillIds` | 建议技能（不自动强开） |
| `preferredConnectorIds` | 建议连接器 |

`SKILL.md` 权威字段：

| 字段 | 含义 |
|------|------|
| `id` | 如 `after-sales-ticket` |
| `name` / `description` | 摘要（常驻系统提示） |
| `triggers` | 短语列表，窄匹配 |
| `requiredConnectorIds` | 缺了则步骤返回 unconfigured，不编数 |
| `optionalConnectorIds` | 有则用，无则跳过 |

连接器 `manifest.json`：

| 字段 | 含义 |
|------|------|
| `id` | `mes` / `dify` / `wecom` / `quote` |
| `title` | 展示名 |
| `kind` | `http` \| `mock` |
| `tools[]` | 将注册的 DSH 工具名（必须 `zr_esc_` 前缀） |
| `defaultEnabled` | P0 全部 **false**（避免抢走 `mes_ask`） |

### 5.2 `state.json`（用户写入）

| 字段 | 含义 |
|------|------|
| `connectors.<id>.enabled` | 是否 register 工具 |
| `connectors.<id>.mode` | `mock` \| `http` |
| `connectors.<id>.baseUrl` / `apiKey` | 密钥落盘，API 回读打码 |
| `skills.<id>.enabled` | 是否进入摘要目录 |
| `sessions.<sessionId>.expertId` | 当前专家；`null` = 不注入人设 |
| `sessions.<sessionId>.pinnedSkillId` | 可选：本会话钉死一个技能 |

新会话、用户点「清除角色」、或 `zr_esc_select_expert` 传入空 id：必须把该 `sessionId` 的 `expertId` 置 `null`。禁止只 set 不清。

### 5.3 工具命名（防碰撞）

| 工具 | 作用 |
|------|------|
| `zr_esc_list` | 列出专家/技能/连接器及启用状态 |
| `zr_esc_select_expert` | 参数 `expertId`（权威）；空字符串=清除 |
| `zr_esc_mes_query` | MES 只读查询（工单/工序/良率） |
| `zr_esc_dify_search` | Dify 知识检索 |
| `zr_esc_wecom_send` | P1，默认关；需 enabled + 明确参数 |

禁止注册与现网冲突的名字：`mes_ask`、`mes_pcb`、`pcb_8d_*`、`zr_cursor_*`、`zr_auto_*`。

## 6. P0 预制资产（结合你们 PCB 落地点）

### 6.1 精选场景（3 张，对标「优先切入」）

| `sceneId` | 标题 | 专家 | 技能 | 连接器 |
|-----------|------|------|------|--------|
| `after-sales-ticket` | 售后工单分析 | 售后支持专家 | 售后工单分析 | MES + Dify |
| `test-case-gen` | 测试用例生成 | 测试专家 | 测试用例生成 | Dify |
| `pcb-process-qa` | PCB 工艺顾问 | PCB 工艺顾问 | （可无技能，仅人设） | Dify 可选 |

点场景 = 把对应 `enabled` 打开 + 当前 `sessionId` 写入 `expertId`。不改其它插件状态。

### 6.2 专家（P0 五个，成本低）

| `id` | 角色 | 方法论要点（写入 EXPERT.md） |
|------|------|------------------------------|
| `pcb-process-advisor` | PCB 工艺顾问 | 开料→钻孔→电镀→蚀刻→阻焊→丝印→表面处理→AOI→成型；答疑区分「工艺知识 vs 现场数据」 |
| `req-analyst` | 需求分析专家 | 模糊口述拆成：范围 / 约束 / 验收 / 待确认问题列表 |
| `test-expert` | 测试专家 | 功能 + 工序异常 + 边界 + 回归；输出必须是用例表不是散文 |
| `after-sales-expert` | 售后支持专家 | 分类→临时围堵→根因假设→对策→是否升级 8D |
| `pm-assistant` | 项目经理助手 | 进度/风险/纪要结构；不替用户发通知（除非企微连接器 P1 已开） |

### 6.3 技能（P0 两个 + 办公一个薄技能）

| `id` | SOP 骨架 | 数据 |
|------|----------|------|
| `after-sales-ticket` | 1. 解析工单要素 2. 调 MES 3. 调 Dify 相似单 4. 根因与对策 5. 严重则提示去用 8D 插件 | 无 MES 则框架+`connector_unconfigured` |
| `test-case-gen` | 1. 抽需求点 2. 套公司用例模板 3. 补异常工序 4. 输出表格 | 无 Dify 仍可纯文档生成 |
| `office-minutes` | 会议纪要：决议 / 待办 / 风险（办公向） | 不依赖连接器 |

P1 再加：`quote-draft`（报价单）、`delivery-pack`（实施文档/培训提纲）、`module-scaffold`（条码/看板/报表脚手架说明——**说明与模板，不调用写码插件**）。

### 6.4 连接器（P0 两个）

#### MES 连接器（`mes`）

| 工具 | 典型用法 |
|------|----------|
| `zr_esc_mes_query` | 「XX 工单卡在哪道工序」「该批良率/报废」 |

查询参数（中文文档，实现时写进 schema description）：

- `kind`：权威枚举 `work_order` \| `yield` \| `scrap` \| `wip`（禁止从用户原话猜）  
- `keyword`：工单号/料号  
- `from` / `to`：可选日期  

适配：

1. **`mock`**：内置 PCB 演示数据（工单 WO-20260918-01、AOI 卡滞、批内 PPM），保证无 MES 也能演示场景卡。  
2. **`http`**：`baseUrl` + Header Token + 路径模板（配置项）。P0 不写死你们未提供的真实路径。

**拿到真实 MES OpenAPI 之前，http 模式只做「配置 + 测通 + 原样 JSON 摘要」，禁止猜测字段名编造业务含义。**

与 `mes_ask` 分工：本连接器是**结构化取数**（给技能 SOP 用）；`mes_ask` 仍是引擎里的自然语言分析。两者都开时，技能正文写明优先 `zr_esc_mes_query`；未启用 ESC 连接器时模型继续用 `mes_ask`。

#### Dify 连接器（`dify`）

| 工具 | 典型用法 |
|------|----------|
| `zr_esc_dify_search` | 知识库检索：工艺规范、历史售后对策、用例模板 |

配置：`baseUrl`、`apiKey`、`datasetId`。调用 Dify 官方检索 HTTP。失败 `error.code=dify_failed`，技能改为「仅按用户粘贴文本分析」，禁止编造知识库条目。

P1：若本机已装 `dsh-knowledge` 且用户在设置勾选「同时检索中软知识库」，再加可选工具；**默认不依赖**该插件。

## 7. UI（对标腾讯，收窄实现）

对齐你提供的 WorkBuddy 截图与蓝图图：

1. **顶区精选场景**：大卡片，一句话 + 绑定的专家/技能小标签。

|------|-----------|---------|

| **本插件** | **`esc`** | **-7** |

## 10. 可行性结论

| 能力 | 可行性 | 依据 |
|------|--------|------|
| 专家人设注入 | **高** | 知识库已用 `system-prompt/assemble` |
| 技能按需加载 | **高** | 知识库 `agent/pre-step` 有界召回同构 |
| 连接器当工具 | **高** | 全仓库插件都是 `defineTool` |
| 侧栏三页签 UI | **高** | 知识库/自动化已占 footer.action |
| 真连公司 MES | **中（卡在接口文档）** | Adapter 可先 mock；http 需你们给路径与鉴权 |
| 真连 Dify | **高** | 官方 retrieval API 稳定；要 datasetId |
| 腾讯级 MCP 商店 / 专家社区 | **本阶段不做** | 产品范围过大，且与公司市场重复 |
| 与 mes_pcb 体验完全合一 | **不追求** | 一个是引擎专家问答，一个是可组合岗位+SOP；并存更安全 |

**总评：P0 可做，且应做成独立插件。** 最大外部依赖是 MES/Dify 的地址与密钥；没有它们也能用 mock + 纯提示词专家演示三层模型。

## 12. 验收清单（P0）

1. 市场或本地安装后，左侧栏出现「专家·技能·连接器」；`GET :18786/health` 正常。  
2. **未点任何场景**时，对话里查产量仍走现网 `mes_ask`（若该 feature 开着），不出现 `zr_esc_mes_query`。  
3. 点场景「售后工单分析」→ 本会话显示售后专家；技能摘要进系统提示；MES/Dify 按配置 mock 或 http。  
4. 用户说「分析工单 WO-20260918-01」→ 模型调用 `zr_esc_mes_query`（kind 为枚举）→ 按技能结构出报告。  
5. MES 未配置且 mode≠mock → 报告含明确「未连接 MES」，`error.code=connector_unconfigured`，**无伪造良率数字**。  
6. 打开测试用例场景，粘贴一段需求 → 输出用例表。  
7. 切换/清除专家后新一轮不再带旧人设；`state.json` 对应 `sessionId.expertId` 已更新或为 null。  
8. 同时使用知识库、自动化、写码插件：侧栏入口都在；端口无冲突；卸本插件后其它功能仍在。  
9. `pack.sh dsh-esc` 后本地 `plugins.json` 仍列出已有公司插件条目。

## 15. 决策摘要（开发前默认按此，改口径需书面）

1. **一个独立 DSH 插件**，不是三个包，也不是引擎 feature。  
2. **三层解耦**：连接器全公司复用，技能按场景沉淀，专家按岗位配置。  
3. **P0 落地点**：Dify + MES（mock 保底）连接器；售后工单分析 + 测试用例生成技能；五个岗位专家；三张场景卡。  
4. **默认不抢** `mes_ask` / `mes_pcb`：连接器关闭则不注册工具。  
5. **技能按需加载**，专家按会话注入，控制流只认 id 字段。  
6. **UI**：左侧栏底部入口 + 面板；不做腾讯社区市场。  
7. **真系统接口**：方案可先开工 mock；http 模式等你提供 MES/Dify 的 URL 与鉴权后再接实。

确认本方案后，下一动作是创建 `dsh-esc/`：store + catalog + 侧栏空态 → mock MES 售后场景跑通 → Dify 可选 → 打包上架。
