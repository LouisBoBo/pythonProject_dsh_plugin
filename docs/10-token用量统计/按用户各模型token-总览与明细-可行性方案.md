# 按用户统计各模型 token：总览与明细可行性方案

> **状态**：桌面用量页已接上（2026-10-26）。总览按供应商 + 模型，明细按任务合并。  
> **页面**：`plugins/dsh-key-quota` 侧栏「用量统计」。当前验收是江西中软工作助手桌面端。  
> **账本**：对话读会话里已经带回的供应商 usage。标题生成和网页搜索的供应商 usage 记在 `~/.dsh/key-quota/side-usage.jsonl`，因为会话格式存不下这两类 usage。不另造 token，不改 `plugins/dsh-llm-meter`。  
> **口径**：合计 = 未命中输入 + 缓存读取 + 缓存写入 + 输出。推理只作明细。  
> 「用量统计规则」是当前桌面用量页的口径。第 7 节起是当初的引擎页方案，不是这次落地的页面。

产品一句话：用户可以在多家模型供应商之间切换。用量页按当前登录账号，给出各「供应商 + 模型」的 token 总览，并可以点进该模型看每一次调用的明细。管理员可以切换到某个用户，或看全员。统计的是 token，不是积分，也不是对话气泡上「用量 376K tok」的缩写。

## 用量统计规则

侧栏「用量统计」只做加法：把供应商已经报回来的 token 加在一起。不按字数估，不把钱换算成 token。

你问一句、模型回一段，这算 **1 次调用**。一轮聊天里问了三次，就是 3 次，三次的 token 分开加。

### 一次调用怎么算

供应商一次调用会带回这几项。页面用下面这个公式：

```text
一次的 token = 没进缓存的输入 + 从缓存读到的输入 + 写进缓存的输入 + 模型写出来的输出
```

推理 token 报了也只留在明细里，**不加进这一次**。供应商要是把推理塞进了总数，页面会先减掉再加。

举例：没进缓存 100，缓存读到 1,000，写进缓存 0，输出 20，推理 50。

```text
这一次 = 100 + 1,000 + 0 + 20 = 1,120
```

推理的 50 不在 1,120 里。

没带回用量的那一次，次数和 token 都不加。不会按字数补一个大概数字。

这四类都会按上面的公式各算一次：

| 你在页面上看到的 | 实际是哪一次 |
| --- | --- |
| 任务名是会话标题 | 给这次聊天起标题 |
| 任务名是网页搜索 | 去网上搜一次。模型名用这次搜索请求里的名字，和聊天用的模型可能不同 |
| 写码卡片 | Cursor 写码，和聊天分开加 |
| 其它任务名 | 一次聊天回复。任务名用这个会话最后定下来的标题 |

同一次调用只加一次。聊天记录里已经有的数，标题或搜索里再出现一遍相同的数，不会再加。

### 一天、一个模型、一个任务

选「按日」，只加选中那一天；选「按月」，把该月每一天加起来。日期按北京时间切，过了晚上 12 点算第二天。个人页只加当前登录这个人的调用。

```text
一天的次数 = 这一天有多少次调用
一天的 token = 这一天每一次的 token 相加

一个模型的次数 = 这家供应商、这个模型名下有多少次
一个模型的 token = 这些次的 token 相加

一个任务的次数 = 这个任务里有多少次
一个任务的 token = 这些次的 token 相加
```

上面的例子如果同一天还有第二次 800、第三次 300：

```text
这一天的次数 = 3
这一天的 token = 1,120 + 800 + 300 = 2,220
```

同一家供应商如果聊天用 `deepseek-flash`、搜索用 `deepseek-v4-flash`，各模型表上是两行。要对这家供应商的账单，把两行的 token 加起来。

调用明细里，同一个任务合成一行，用的就是上面「一个任务」的公式。卡片和各模型仍按每一次相加，合成一行只是为了好读，token 不会变少。明细一页 10 条；列表最多展开最近 200 次再合并，卡片上的次数和 token 仍是全部加总。

卡片上的 `1.34M` 是 1,340,000 这种完整数字的简写，公式没有变。鼠标放在数字上可以看到完整值。

### 和供应商账单怎么对

账单 = 供应商那边计费的每一次。用量页 = 我们已经拿到用量数字的每一次，再按上面的公式相加。

标题和网页搜索从这次改动之后，只要供应商把用量带回来，就按同一次的公式加进页面。这次改动之前已经发生、当时又没把用量存下来的那些次，加不进去，也不会估一个数补上。

## 0. 结论

可行。一次模型调用已经写成一行流水，行上有 `user_id`、`provider`、`model`、`lane` 和 token 分项。总览是对这些行按「供应商 + 模型」求和；明细是同一批行按时间倒序分页。缺的是分组键和两屏界面，不是新的采集链路。

对话红框上的每轮用量不能当这张表的数据源。那个数字是一轮里多次调用加总后的界面缩写；某一轮对不上时整轮不显示。本方案只读已经落盘的调用流水。

| 做                                      | 不做                                              |
| -------------------------------------- | ----------------------------------------------- |

## 2. 现状（2026-10-26）

写入时 `append_event` 已经带齐维度：


| 字段                                                                                 | 含义                                     |
| ---------------------------------------------------------------------------------- | -------------------------------------- |
| `user_id`                                                                          | 入库时的平台登录账号。计量文件里自带的用户 id 不采用，避免多账号串账   |
| `provider`                                                                         | 这一次实际请求的供应商                            |
| `model`                                                                            | 这一次的模型                                 |
| `lane`                                                                             | 用途：对话、标题、记忆、知识库、写码等。展示名在 `LANE_LABELS` |
| `prompt_tokens` / `cache_read_tokens` / `cache_write_tokens` / `completion_tokens` | 未命中输入、缓存读取、缓存写入、输出                     |
| `reasoning_tokens`                                                                 | 推理。只在明细里，不加进合计                         |
| `total_tokens`                                                                     | 合计。入库时若等于「分项 + 推理」，引擎会改回不加推理的合计        |
| `quality`                                                                          | `provider` 表示供应商回传了用量；`missing` 表示没回传  |
| `ts`                                                                               | 调用时间，汇总按 Asia/Shanghai                 |
| `job_id`                                                                           | 调用 id，明细用来去重和对账                        |


读取侧已经有：

- `GET /api/usage/summary`：当前登录账号的区间汇总。模型列表在 `llm.models` / `cursor.models`。
- `GET /api/usage/events`：当前登录账号的流水分页，带 `label`（用途中文名）。
- 企业侧已有按人的汇总接口（`/api/usage/enterprise/people` 等），管理员才能看别人。

和本方案之间的缺口：

1. `summarize` 按模型名合并。`provider` 只是挂在该模型桶上的一个字符串。两家供应商若模型 id 相同，会并成一行，供应商也会被盖住。
2. `list_events` 只能按来源（`llm` / `cursor`）和某一天过滤，不能按供应商、模型、日期区间过滤。
3. 用量页是按日/按月的合计和模型条，没有「总览表 → 点进明细」这两屏。
4. 会话补采把 `source.provider` 折进 `model` 字符串，补采行的供应商维度弱于计量流水。计量启用之后，启用前的会话/标题/记忆只补到首条计量之前，启用后以计量为准，不会双计。

## 3. 统计单位

一行 = 一次已经结束的模型调用，不是一轮对话，也不是一个会话。

用户中途从 DeepSeek 换到智谱，下一行的 `provider` / `model` 不同。总览把这些行加在一起；明细仍是多行。

合计只加 `total_tokens`（已按冻结口径纠正过的值）。同时给出三档，便于和现有用量页对齐：

- 未命中输入：`prompt_tokens`（与缓存读取互斥分列时，未命中就是 prompt）
- 缓存读取：`cache_read_tokens`
- 输出：`completion_tokens`

`quality=missing` 的行保留在明细里，次数计入「未回传」，token 加 0。禁止用字符数或红框数字去估。

归属：

- 个人页只认 `user_id` 等于当前登录账号。空 `user_id` 不对全员可见。
- 管理员查看某人时，显式传入该 `user_id`，仍按同一字段过滤。
- 用量跟账号，不跟电脑。

## 4. 总览界面

入口仍是工作助手用量页。个人只看自己。管理员多一个用户选择：自己、某一个用户、全员。

筛选：今天、7 天、30 天、自选起止日期。时区 Asia/Shanghai。默认 7 天。

上方四块数字（所选用户、所选时间）：


| 块         | 内容                   |
| --------- | -------------------- |
| 调用次数      | 全部行数，另注未回传次数         |
| token 合计  | 各行 `total_tokens` 之和 |
| 未命中输入     | prompt 之和            |
| 缓存读取 / 输出 | 两档分别求和               |


下方一张表，一行是一个「供应商 + 模型」。来源 `llm` 与 `cursor` 分两段，避免写码和对话模型混在一张表里却分不清来源。


| 列     | 规则                                        |
| ----- | ----------------------------------------- |
| 供应商   | `provider`，空则显示「未标注」                      |
| 模型    | `model`，空则显示 `unknown`                    |
| 调用次数  | 该键下的行数                                    |
| 未回传   | `quality=missing` 的行数                     |
| token | 该键下 `total_tokens` 之和                     |
| 占比    | 该行 token / 本表所在来源（llm 或 cursor）的 token 合计 |


排序：token 降序，相同则按供应商、模型名。点击一行进入明细，并带上当前的用户、时间、供应商、模型。

全员总览在同一张表上再加「用户」列，或先按用户汇总再点进该用户的模型表。v1 采用后者：全员先是用户列表（已有按人汇总），点用户后再看该用户的模型表。不在第一屏把「人 × 供应商 × 模型」铺成一张大表。

## 5. 明细界面

与总览共用用户和时间条件。从总览点进来时，供应商和模型已填好；也可以清空，看该用户在这段时间的全部调用。

一行一次调用，时间倒序：


| 列     | 字段                         |
| ----- | -------------------------- |
| 时间    | `ts`                       |
| 用途    | `lane` 的中文名（`LANE_LABELS`） |
| 供应商   | `provider`                 |
| 模型    | `model`                    |
| token | `total_tokens`             |
| 状态    | 已计量 / 未回传（由 `quality` 决定）  |


展开一行时再显示未命中输入、缓存读取、缓存写入、输出、推理。推理不进合计，展开区标明「不计入合计」。

不展示：用户原文、系统提示词、API Key、完整请求体。用途已经能区分「对话 / 生成标题 / 整理上下文 / 自动化」。

分页沿用现有接口，默认每页 10 条，上限 50。导出当前筛选的全部行（不受当前页限制），列为上表加上调用 id。导出失败不影响页面。

## 6. 接口改动

不新增账本，不改写入字段。只扩展两个只读接口。

### 6.1 汇总 `GET /api/usage/summary`

现有查询参数保留：`days`、`on`、`source`、`grain`。个人仍只统计 Bearer 对应用户。

模型桶的键从「模型名」改为「来源 + 供应商 + 模型」。返回的每一项至少包括：

```text
provider, model, calls, tokens, missing_calls, cache_hit, cache_miss, output
```

`llm.models` 与 `cursor.models` 的数组结构保留，避免旧页面读 `model` / `tokens` 时直接坏掉。同一模型名、不同供应商变成数组里的两项，不再互相覆盖 `provider`。

管理员看他人：增加可选 `user_id`。仅管理员可传；不传时仍是当前登录用户。传 `all` 时不按人过滤，并在响应里增加 `by_user`（用户 id、调用次数、token），供全员第一屏。普通人传别人的 id 返回 403。

### 6.2 流水 `GET /api/usage/events`

在现有 `page`、`page_size`、`source`、`on` 之外增加：


| 参数            | 含义                                               |
| ------------- | ------------------------------------------------ |
| `provider`    | 精确匹配供应商；空表示不限                                    |
| `model`       | 精确匹配模型；空表示不限                                     |
| `from` / `to` | 起止日期 YYYY-MM-DD，含首尾，上海时区。与 `on` 互斥，有 `on` 时只看那一天 |
| `user_id`     | 仅管理员。规则与汇总相同                                     |


响应仍是 `{ events, total, page, page_size }`。每条继续带 `label`。增加同筛选条件下的 `export=1` 时，返回当前筛选的全部行（设上限，例如 5000），超过则要求缩小日期。普通翻页不走导出。

鉴权与现用量 HTTP 一致：有效 Bearer，已改默认密码的存活账号。不以 `active.json` 回落。

## 7. 页面改动

只改 `engine/app/static/index.html` 的用量区（以及它已经在调的 summary / events）。

1. 总览表绑定新的 `models[]`（含 `provider`）。旧的按日柱状可以留在总览下方，不作为本方案的验收对象。
2. 行点击把 `provider`、`model`、日期写入明细筛选并切换到明细屏。
3. 明细表绑定 `events`。未回传行 token 显示 0，状态显示「未回传」。
4. 管理员的用户选择调用带 `user_id` 的 summary / events。

`dsh-key-quota` 的用量图表不复制这两屏。它继续只读引擎流水做 Key 限额。若插件页上的「按模型」条仍把供应商折进模型名，与本方案无关，不在本次改。

## 8. 实施顺序

1. **汇总分组**：`summarize` 按 `source + provider + model` 分桶，补测试：同名模型两家供应商得到两行；空供应商单独成行；`missing` 不增加 token。
2. **流水筛选**：`list_events` 增加供应商、模型、日期区间；个人越权看别人被拒绝。
3. **总览表**：用量页改读新的模型数组，点击进入明细。
4. **明细表与导出**：分页、展开分项、导出当前筛选。
5. **管理员**：用户列表 → 该用户的总览 → 该用户的明细。全员第一屏复用现有按人汇总，不新写账本。

每一步都可以单独验收。第 1 步不改页面也能用接口对账。

## 9. 验收

用同一账号连续调用两家供应商的两个模型（或同一模型 id 的两家，若环境里有），再触发一次不回传用量的调用（例如标题模型）。

- 总览出现两行（或三行），token 等于这两次调用的 `total_tokens` 之和，未回传那次次数 +1、token 不加。
- 点其中一行，明细只有该供应商和该模型，时间、用途、token 与流水一致。
- 换一个平台账号登录，看不到上一账号的行。
- 管理员指定上一账号后，看到的合计与该账号自己看到的一致。
- 推理 token 出现在展开区，合计里没有把它再加一遍。
- 导出的行数等于明细的 `total`，且不含原文和 Key。

---



## 10. 边界

1. 供应商没回传用量时，明细有行、token 为 0。总览会少计 token，未回传次数用来发现这种情况。不回填估算值。
2. 不走计量流水的调用不会出现。计量启用前的会话补采只覆盖首条计量之前；启用后的对话、标题、记忆以计量为准。引擎自己直连的 PCB、审码若已 `append_event`，会在对应 `lane` 里出现。
3. 缓存读取计入 token 个数，不表示金额。本方案没有单价。
4. 写码在 `cursor` 段，对话在 `llm` 段。总览不要把两段 token 加成一个「模型消耗」而不标注来源。
5. 保留天数仍是账本现有的 90 天。更早的调用不在总览和明细里。
