# 重启服务方案

> 日期：2026-11-18。插件 `@zhongruan/dsh-cursor-chat`（仓库 0.3.82）。  
> 实现：`plugins/dsh-cursor-chat/src/opsRestart.ts`，收口在 `orchestrator/runJob.ts` 的重启段。  
> 后续重启服务先按本文做。项目结构和本文不完全一样时，沿用该项目自己的命令，灵活处理，不要另起一套工具链。

写码、改页面、修 bug 仍走沙箱。跑测试、装依赖、看日志、查环境、排障仍由 Cursor 在项目终端执行，但是否完成只认工具终态（退出码 / 工具状态），不认模型正文里的「已完成」；没过再纠错一轮，仍不过就标未完成。  
「启动 / 重启 / 把服务拉起来」走本文。只有插件一张启动计划都认不出时，才降级交给 Cursor SDK。已经认出命令、只是某一侧没在听，不得再交给 Cursor。

## 为什么优先不交给 Cursor SDK

Cursor IDE 能留住服务，是因为终端挂在 IDE 上，不挂在这一轮 Agent 上。SDK 里用 `nohup` / `setsid` 拉起的进程会随这一轮结束被回收：脚本当时能打出 HTTP 200，会话一结束端口又空了。macOS 上没有 `setsid`。桌面客户端的 PATH 里也没有 nvm，`command -v npm` 失败时旧逻辑会把前端当成「没有启动命令」，只拉后端，再把缺的前端交给 Cursor。

插件自己拉起时，进程用 `spawn({detached:true})` 脱离会话。启动程序退出后，父进程应是系统 `launchd`（或 Windows 上独立的 `Start-Process`），而不是这一轮 Agent。

2026-11-18 在 `pythonProject_zr_aicoding` 用去掉 nvm 的 PATH 验过：能同时认出后端 `app.main:app :8009` 和前端 `vite :5175`；只拉前端时，启动进程退出后 `http://127.0.0.1:5175/` 仍返回 200。端口以该项目配置为准，不是写死的。

## 认不出命令时怎么办

两侧（或点名的一侧）都找不到启动命令时：

1. 进度写明「项目里没有现成启动命令，改由 Cursor 按 IDE 方式在项目终端处理」。
2. 把同一轮诉求交给 Cursor SDK（`phase=ops`），提示它像 IDE 一样读 README / 脚本 / compose / Makefile / 现有终端，找出项目自己的启动方式再后台拉起。
3. 仍然禁止编造与本项目无关的命令，禁止为了启动去改代码。

已经认出命令时不走上面的降级：先拉起，再按端口验收（最多两轮）。都在听才算完成。有一侧没在听，把缺的一侧和日志写进进度，按同一命令再拉起一次。仍然没在听就失败收口，不再降级 Cursor。判断在听时要同时看到「在听」，并且整句不是「未监听」——「未监听」这四个字里含有「在听」。

## 拉起方式

和 Cursor IDE 成功的那次相同：

1. 从项目配置读出目录、命令和端口。
2. 停掉占用该端口、且属于本项目这条命令的进程。
3. **按操作系统分派（禁止混用）**：

| 平台 | 拉起 | 停本项目端口进程 | 前端可执行文件 |
| --- | --- | --- | --- |
| Windows | `Start-Process`（`launchWindows`） | PowerShell `Get-NetTCPConnection` + 命令行含本项目目录 | `npm.cmd`（无扩展名 `npm` 失败再改 `.cmd`）；**不要**改成直拉 vite.js |
| macOS / Linux | `spawn({detached:true})` + `unref`（`launchPosix`） | `lsof` + `ps` 命令行含本项目标记 | 桌面 PATH 没有 nvm 时，按 nvm 默认别名、已装最高版本、fnm、volta、homebrew、当前 `node` 可执行文件找 Node。有 `node_modules/vite/bin/vite.js` 就用这个 Node 直拉 `vite.js --host 0.0.0.0 --port --strictPort`，不用 npm 包装进程 |

标准输出/错误分文件写到项目 `.dev-logs/` 并写 pid。Python 用项目 `.venv` / `venv`，否则系统解释器（Windows 跳过 `WindowsApps` 商店占位）。
4. 等到页面或接口有响应再算成功。后端先看 `/api/health`，没有这个路径但进程已经在听，也算起来了。失败时把错误日志带回，不要只说端口没开。
5. 拉起每一侧之前、确认在听之后，都写进进度（进度里标明平台）。终态结论只保留结果和这些步骤，不把同一句再贴一遍。查端口和拉起进程需要大约一分钟，这段时间进度卡应能看到正在拉起哪一侧。
6. 只有「一张命令都没有」才走 Cursor。这条降级结束前必须再交回插件，用上面的脱离会话方式稳拉一次。禁止把 Agent 终端里的 `nohup` 当成终态。
7. 失败结论以端口探测为准。结果行写哪一侧没在听，不采用 Cursor 正文里的「已重启并在监听」，也不再写「请你验收」。成功才给本机地址。

## 命令从哪里读

先按下面的常见结构认。认到就用项目里的脚本，不改端口，不换命令。

| 一侧 | 在哪里找 | 用什么命令 |
| --- | --- | --- |
| 前端 | `frontend`、`web`、`client`、`apps/web`，或仓库根目录。目录名是这几个，或依赖里有 Vite / Next / Webpack / Vue | `package.json` 的 `dev`，没有再用 `start`，再没有用 `serve`。端口读 Vite 配置里的 `port` |
| 后端 | `backend/app/main.py` 或仓库根目录 `app/main.py`、`main.py`，文件里有 FastAPI | `python -m uvicorn <模块> --host 127.0.0.1 --port <端口> --reload`。端口读 Vite 代理到本机的地址 |
| 后端另一类 | 同一目录有 Django `manage.py` | `python manage.py runserver 127.0.0.1:<端口>` |
| 只有一个应用 | 分不出前后端，根目录有一条普通启动脚本 | 只跑这一条 |

`git fetch`、`git merge`、`git pull`、`pull-refresh` 不是启动命令，禁止执行。

## 灵活处理

常见结构对不上时，仍然只做重启，并遵守这些边界：

- 项目里已经写明的启动方式优先：`package.json` 脚本、实际存在的配置、脚本参数里的端口。读到了就用那条，不要换成 uvicorn 或 `npm run dev` 的固定写法。
- 端口以项目配置为准。Vite 的 `port`、代理地址、脚本里写明的端口都可以。配置里没有的端口不要猜一个新的。
- 用户点名要两侧、但只找到一侧时：拉起找到的那一侧，缺的一侧验收失败，不把已认出的命令交给 Cursor。
- 两侧都找不到时：不要编命令；降级 Cursor SDK，按上一节「认不出命令时怎么办」继续，禁止空手失败。
- 进程起了但业务代码报错（例如导入失败）时，把日志里的报错带回。重启这一步不改业务代码。
- 停进程只停本机回环、且命令行含本项目工作目录的进程。认不出是本项目的进程时，不要杀；禁止「凡占端口就杀」。

## 不要做的事

- 不要在插件已认出命令时，因为慢、或某一侧没在听，再丢给 Cursor SDK。
- 不要因为桌面 PATH 里没有 npm，就把前端当成没有启动命令。
- 不要用插件自己发明的另一套端口或另一套框架命令。
- 不要把标准输出和错误日志写进同一个文件。Windows 的 `Start-Process` 不允许。
- 不要执行会 `git pull` / `git merge` 的刷新脚本。
