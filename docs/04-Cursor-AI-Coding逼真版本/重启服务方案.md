# 重启服务方案

> 日期：2026-11-12。插件 `@zhongruan/dsh-cursor-chat`。  
> 实现：`plugins/dsh-cursor-chat/src/opsRestart.ts`。  
> 后续重启服务先按本文做。项目结构和本文不完全一样时，沿用该项目自己的命令，灵活处理，不要另起一套工具链。

写码、改页面、修 bug 仍走沙箱。跑测试、装依赖、看日志、查环境、排障仍交给 Cursor。  
「启动 / 重启 / 把服务拉起来」**优先**走本文；只有插件一张启动计划都认不出时，再降级交给 Cursor SDK，按 Cursor IDE 方式在真实项目终端继续处理，禁止需求落空。

## 为什么优先不交给 Cursor SDK

Cursor IDE 能重启服务。SDK 接手要等本地执行器，经常要几分钟，接手后还容易先搜仓库。常见项目里启动命令已经写好，插件直接读配置拉起更快、更稳。

已在 `pythonProject_zr_aicoding` 对照 Cursor IDE 验过：后端 `http://127.0.0.1:8009/api/health` 返回 `{"status":"ok"}`，前端 `http://127.0.0.1:5175/` 返回 200。端口以该项目配置为准，不是写死的。

## 认不出命令时怎么办

两侧（或点名的一侧）都找不到启动命令时：

1. 进度写明「项目里没有现成启动命令，改由 Cursor 按 IDE 方式在项目终端处理」。
2. 把同一轮诉求交给 Cursor SDK（`phase=ops`），提示它像 IDE 一样读 README / 脚本 / compose / Makefile / 现有终端，找出项目自己的启动方式再后台拉起。
3. 仍然禁止编造与本项目无关的命令，禁止为了启动去改代码。
4. 若插件已经认出命令、只是进程没起来，带 `.dev-logs` 失败收口，**不再**降级 Cursor 瞎搜。

## 拉起方式

和 Cursor IDE 成功的那次相同：

1. 从项目配置读出目录、命令和端口。
2. 停掉占用该端口、且属于本项目这条命令的进程。
3. Windows 用 `Start-Process` 后台拉起。标准输出和错误日志分成两个文件，写到项目 `.dev-logs/`。前端可执行文件用 `npm.cmd`，不要用没有扩展名的 `npm`。Python 用项目 `.venv` / `venv`，否则用系统里的 `python.exe`，跳过 `WindowsApps` 里的商店占位。
4. 等到页面或接口有响应再算成功。后端先看 `/api/health`，没有这个路径但进程已经在听，也算起来了。失败时把错误日志带回，不要只说端口没开。
5. 拉起每一侧之前、确认在听之后，都写进进度。终态结论只保留结果和这些步骤，不把同一句再贴一遍。查端口和拉起进程需要大约一分钟，这段时间进度卡应能看到正在拉起哪一侧。

## 命令从哪里读

先按下面的常见结构认。认到就用项目里的脚本，不改端口，不换命令。

| 一侧 | 在哪里找 | 用什么命令 |
| --- | --- | --- |
| 前端 | `frontend`、`web`、`client`、`apps/web`，或仓库根目录。目录名是这几个，或依赖里有 Vite / Next / Webpack / Vue | `package.json` 的 `dev`，没有再用 `start`，再没有用 `serve`。端口读 Vite 配置里的 `port` |
| 后端 | `backend/app/main.py` 或仓库根目录 `app/main.py`、`main.py`，文件里有 FastAPI | `python -m uvicorn <模块> --host 127.0.0.1 --port <端口> --reload`。端口读 Vite 代理到本机的地址 |
| 后端另一类 | 同一目录有 Django `manage.py` | `python manage.py runserver 127.0.0.1:<端口>` |
| 只有一个应用 | 分不出前后端，根目录有一条普通启动脚本 | 只跑这一条 |

`git fetch`、`git merge`、`git pull`、`pull-refresh` 不是启动命令，禁止执行。

## 灵活处理

常见结构对不上时，仍然只做重启，并遵守这些边界：

- 项目里已经写明的启动方式优先：`package.json` 脚本、实际存在的配置、脚本参数里的端口。读到了就用那条，不要换成 uvicorn 或 `npm run dev` 的固定写法。
- 端口以项目配置为准。Vite 的 `port`、代理地址、脚本里写明的端口都可以。配置里没有的端口不要猜一个新的。
- 只找到前端或只找到后端时，拉起找到的那一侧，另一侧写进结果说明。
- 两侧都找不到时：不要编命令；降级 Cursor SDK，按上一节「认不出命令时怎么办」继续，禁止空手失败。
- 进程起了但业务代码报错（例如导入失败）时，把日志里的报错带回。重启这一步不改业务代码。
- 停进程只停本机回环、且命令行含本项目工作目录的进程。认不出是本项目的进程时，不要杀；禁止「凡占端口就杀」。

## 不要做的事

- 不要在插件已认出命令时，仅仅因为慢就再丢给 Cursor SDK 搜一遍。
- 不要用插件自己发明的另一套端口或另一套框架命令。
- 不要把标准输出和错误日志写进同一个文件。Windows 的 `Start-Process` 不允许。
- 不要执行会 `git pull` / `git merge` 的刷新脚本。
